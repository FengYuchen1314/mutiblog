# 15 · 交付给实现模型的操作指南

> 这套规格总量约 8000 行。**没有任何模型能在一个上下文里可靠地消化并实现它。**
> 本文档定义如何把它切成可执行的批次，以及每批需要携带什么。
>
> 读者是**调度者**（把任务分发给编码模型的人或流程），不是编码模型本身。

## 0. 开工前必须先产出的东西（"第 0 批"）

**这套规格现在可以开工，但不能直接整份丢给模型。** 有五样东西规格里只有描述、没有实体，模型会各自发明，然后在批次之间对不上。必须先做完这一批（约 **2 人日**），再进 M0。

| # | 产出物 | 为什么必须先做 | 交付形态 |
|---|---|---|---|
| **0.1** | **锁定的依赖版本清单** | 规格里写的是 `chi v5`、`shiki` 这种粒度。Shiki v1 与 v3 的 API 不兼容（`getHighlighter` → `createHighlighter`），不同批次的模型选到不同版本就会互相打架 | `backend/go.mod` + 三个 `package.json` 的**完整版本号**，先跑通 `go mod download` 与 `npm ci` |
| **0.2** | **`api/openapi.yaml` 骨架** | docs/07 是**给人看的表格**，不是机器可读的 schema。M2 产出 API、M3 前端消费，两个批次对字段名理解不一致就崩。这是前后端唯一的契约载体 | 至少覆盖 auth + posts + categories 的完整 schema；其余端点可留 stub 逐批补 |
| **0.3** | **`internal/model` 的完整 Go 源文件** | 规格里的 struct 是**片段**（省略号、注释掉的字段）。它是所有包的依赖根，必须先定死 | 可编译的 `.go` 文件，含全部 struct + json/yaml tag + `LocalizedString` 的编解码 |
| **0.4** | **testdata 生成器** | 多个验收标准引用了不存在的数据集："testdata/ 中的 20 篇多语言文章"、"1000 篇 × 4 语言"、"正文合计 200MB"。没有它，性能与索引类验收无法执行 | `backend/testdata/gen/main.go`，参数化生成规模可控的语料（含中日德文、代码块、公式、表格、mermaid） |
| **0.5** | **「魔鬼测试文章」** | [docs/06 §9](06-ai-translation.md) 的 T1–T22 全部依赖它。它同时也是 M5 渲染验收（R1/R2）的输入 | 一个 `.md` 文件，包含全部 22 类元素，附一份"翻译后应保持不变的片段"清单 |

**0.1 的具体风险**：我在规格里对 Shiki transformer 的描述**已经出过一次错**（编造了不存在的 `transformerCopyButton`，见 [docs/04 §4.2 勘误](04-render-pipeline.md)）。这类错误只有在真正 `npm ci` 并跑通一次最小管线后才会暴露。**第 0 批必须包含一个 hello-world 级的端到端验证**：一段含代码块+公式的 Markdown → 经完整 unified 管线 → 输出 HTML。跑通了，M5 才有地基。

### 0.6 建议的第 0 批交付顺序

```
① 建仓库骨架 + go.mod + 三个 package.json，全部装上并锁版本
② 写 internal/model 全部类型，go build 通过
③ 写最小 unified 管线 demo，验证 shiki/katex/gfm 实际可用   ← 会抓出规格里的 API 错误
④ 从 model 生成 openapi.yaml 骨架，跑通 make api-types
⑤ 写 testdata 生成器 + 魔鬼测试文章
```

③ 是最有价值的一步——它用最小成本验证整条 Node 侧技术栈，而这正是规格中我最没把握的部分。

## 1. 核心原则

| 原则 | 说明 |
|---|---|
| **一次一个里程碑** | 不要让一个会话同时做 M3 和 M4。里程碑边界就是上下文边界 |
| **宪法必须每次携带** | `PLAN.md §0`（8 条不可协商约束 + 技术选型）无论做哪一批都要放进上下文 |
| **只给需要的文档** | 做 M9（AI 翻译）不需要 docs/09（主题）。多给的每一份都在稀释注意力 |
| **验收标准先行** | 把该里程碑的验收清单放在提示词开头，而不是结尾 |
| **产出物必须包含测试** | 没有测试的实现视为未完成，因为下一批无法信任它 |
| **接口冻结** | 上一批产出的公开类型与函数签名，下一批不得随意改动；确需改动要显式说明并同步调用方 |

## 4. 跨批次一致性的机制化保障

人工同步类型定义必然漂移。必须用机制而不是纪律来解决。

### 4.1 类型定义的单一源

当前有三处需要保持一致：Go struct ↔ `openapi.yaml` ↔ TS interface。我原来只解决了后两者（openapi → TS 代码生成），Go 与 openapi 之间仍是手抄，**跑几个月必然不一致，且错误在运行时才暴露**。

**修正：以 Go struct 为唯一源。**

```
internal/model/*.go  （带 json tag，唯一真相源）
        │
        ├── go generate → api/openapi.yaml      （用 swaggo 或自写生成器）
        │                        │
        │                        └── openapi-typescript → frontend/admin/src/api/schema.d.ts
        │
        └── go generate → frontend/shared/src/types.ts   （渲染器与主题用）
```

`Makefile`：
```make
generate:
	cd backend && go generate ./...
	npx openapi-typescript backend/api/openapi.yaml -o frontend/admin/src/api/schema.d.ts

check-generated: generate
	git diff --exit-code || (echo "生成物未提交，请运行 make generate"; exit 1)
```

**`check-generated` 进 CI**，任何 PR 忘记重新生成都会红。这把"纪律问题"变成了"机器问题"。

### 4.2 每批结束的交接清单

实现者在交付时必须产出：

```markdown
## 本批交付
- 新增包：internal/xxx（职责一句话）
- 公开接口：<go doc 输出>
- 新增配置项：<键名 + 默认值 + 是否可热重载>
- 新增 SQLite 迁移：0005_xxx.sql
- 新增事件：XxxChanged
- 新增 CLI 子命令：xxx

## 与规格的偏离
- <哪一条、为什么、影响是什么>

## 遗留
- <明确列出未实现的部分及原因>
```

这份清单是下一批的输入。**没有它，下一批会重复造轮子或调用不存在的函数。**

### 4.3 每批结束的回归

```bash
make test && make check-generated && ./blog-server doctor
# M6 之后追加：
./blog-server verify --sample 100
```

## 4.4 三批高风险，需要额外准备

| 批次 | 风险 | 应对 |
|---|---|---|
| **M5 渲染器** | 规格中技术不确定性最高的部分。React 19 两遍渲染 + island 的 hydration 标记匹配，我给的是**设计方案而非验证过的代码**。若 `hydrateRoot` 对 `renderToString` 产出的子树报 mismatch 警告，需要现场调整 | 第 0 批的 ③ 先验证 unified 管线；M5 拆成四小批，第一小批只做"Markdown → HTML 字符串"不碰 React |
| **M9 AI 分段器** | 全系统技术密度最高的单点。goldmark 拿 inline 节点的**字节区间**有坑（`node.Lines()` 对 inline 节点不总是可用，需从 `text.Segment` 推导），我在规格里写的是伪代码 | 独占一个会话；先只做块级抽取并用 T1–T22 验证，行内占位符作为第二步；**必须先写测试再写实现** |
| **M3 编辑器** | 体量最大的前端工作（CodeMirror 6 扩展、三层保存、冲突对话框、斜杠命令）。模型容易做出"能跑但细节全丢"的版本 | 拆成三小批；每小批的验收标准逐条列出，不接受"基本可用" |

## 5. 已知的高危区域（提醒实现者重点关注）

这些地方我预判模型最容易做错，投喂时应显式点名：

| 区域 | 常见错误 | 防范 |
|---|---|---|
| **Front Matter 序列化** | 用 `yaml.Marshal` 直接输出 → map 顺序不稳定 → 每次保存 git diff 全是噪音 | 必须手工构造 `yaml.Node`，字段顺序硬编码 |
| **AI 分段回填** | 用字符串替换而非字节区间 → 内容中有重复文本时替换错位置 | 严格用 `[Start,End)` 偏移，正序拼接 |
| **权威字段镜像** | 保存派生语言时忘记用源覆写 → 各语言分类不一致 | `mirrorFromSource` 必须在保存路径上无条件调用 |
| **`AffectedUnits`** | 忘记处理"变更前"的分类/slug → 幽灵页面 | `Change` 必须带 `Before` 快照；写完跑 `verify` |
| **分页边界** | 只重渲染前几页 → 后续页面静默错乱 | 见 docs/04 §2.1 修订版 |
| **自写抑制** | 靠 fsnotify 事件类型判断 → 写入循环 | 必须用 `Suppress(path)` 时间窗 |
| **锁跨越 IO** | 持索引写锁读文件 → 长时间阻塞所有读 | 先在锁外解析，再拿锁替换 |
| **超时嵌套** | 外层超时 < 内层 → 永远拿不到真实错误 | `validateTimeoutOrdering()` 启动自检 |
| **`attempts` 语义** | 进程崩溃回收时也 +1 → 重启几次任务就永久失败 | 只有任务自身返回错误才 +1 |
| **确定性渲染** | 输出里带构建时间戳 → `verify` 永远有 diff | 见 docs/14 §4.3 |
| **Secure Cookie** | 默认 true + HTTP 访问 → 登录死循环 | `auto` 模式 + 前端自检 |
| **symlink 挂载** | 反代挂 `generated/public` → 重建后不生效 | 挂父目录 |

## 6. 建议的推进节奏

```
第 1 周   M0 + M1        （地基，慢一点没关系，错了后面全塌）
第 2 周   M2 + M3①②      
第 3 周   M3③ + M4        （编辑器是硬骨头）
第 4 周   M5              （渲染器打通，第一次看到完整页面）
第 5 周   M6 + M7         （站点成形）
第 6 周   M8 + M9①        
第 7 周   M9②③④          （AI 翻译全链路）
第 8 周   M10 + M11       
第 9 周   M12 + 走查修复    
```

**里程碑之间必须有一次人工验收**，不要连着跑三个批次再一起看——错误会复利。

M5 结束时应该有第一个"能看的东西"（一篇文章渲染成完整 HTML 页面）。如果到 M5 结束还看不到，说明前面某处偏离了，停下来排查而不是继续往前推。
