# 12 · 可靠性、失败模式与体验细节

> 前 11 份文档描述系统**正常工作**时的样子。这一份描述它**出问题**时的样子——以及用户在每一秒看到什么、能点什么。
>
> 核心原则：**任何超过 1 秒的操作都必须有真实进度；任何可能卡住的东西都必须有看门狗；任何失败都必须有用户能执行的下一步动作。**

---

## 1. 长任务的进度模型

### 1.1 统一的进度结构

所有长任务（渲染、翻译、备份、导入、重建）用同一个进度结构，通过 SSE 推送：

```ts
interface Progress {
  jobId: string;
  kind: 'render' | 'translate' | 'backup' | 'import' | 'rebuild';
  phase: string;            // 阶段标识，见下
  phaseLabel: string;       // 已本地化的人类可读文案
  done: number;             // 已完成的最小单位数
  total: number;            // 总数；-1 表示未知
  current?: string;         // 当前正在处理的对象（文件名/URL/语言）
  startedAt: string;
  etaSeconds?: number;      // 仅当 total 已知且 done >= 3 时才给出
  failed: number;           // 已失败的单位数
  canCancel: boolean;
  stalled: boolean;         // ★ 超过 stallThreshold 没有进展
}
```

### 1.2 真进度 vs 假进度

**禁止**输出无意义的百分比。每个任务的进度必须来自可数的真实单位：

| 任务 | 最小单位 | total 何时可知 | 未知阶段的表现 |
|---|---|---|---|
| 渲染 | RenderUnit | 入队时立刻可知 | — |
| 全量重建 | RenderUnit | 枚举完成后可知 | `phase: enumerating`，显示不确定态进度条 |
| 翻译 | 批次 (batch) | **分段完成后**才可知 | `phase: segmenting`，显示"正在分析文章结构…" |
| 备份 | 文件数 | walk 完成后可知 | `phase: scanning`，显示"正在统计文件…" |
| 导入 | 文件数 | 解压后立刻可知 | — |

**ETA 计算**：`(now - startedAt) / done * (total - done)`，但：
- `done < 3` 时不显示 ETA（样本太少，跳变难看）
- ETA > 1 小时时显示"预计较长时间"而非具体数字
- ETA 只允许**单调下降或小幅上调**（用 EMA 平滑，`α=0.3`），禁止来回跳

### 1.3 阶段定义

```
render:    queued → rendering → writing → done
rebuild:   enumerating → rendering → assets → validating → switching → done
translate: queued → segmenting → translating(batch i/n) → assembling → validating → writing → rendering → done
backup:    scanning → archiving → checksumming → done
import:    extracting → parsing → validating → writing → indexing → rendering → done
```

每个阶段在 UI 上显示为一个步骤条，已完成的打勾，当前的转圈，未开始的置灰。**用户永远知道系统在做什么**。

## 2. 全系统超时矩阵

**铁律：外层超时必须严格大于内层超时。** 否则内层的错误信息永远拿不到，用户只看到笼统的"请求超时"。

| # | 层 | 超时 | 说明 |
|---|---|---|---|
| 1 | 浏览器 fetch（AbortController） | 60s | 普通 API |
| 2 | 浏览器 fetch（上传） | 300s | 大文件 |
| 3 | Nginx `proxy_read_timeout` | 90s | 必须 > #1 |
| 4 | Go `http.Server.ReadHeaderTimeout` | 10s | 防慢速攻击 |
| 5 | Go `http.Server.WriteTimeout` | **0（禁用）** | 否则 SSE 会被切断；改用 per-route 超时 |
| 6 | `middleware.Timeout` (`/api/*`) | 55s | 必须 < #1，让 Go 先返回结构化错误 |
| 6b | 豁免路由 | — | `/api/admin/events`(SSE)、`/backup/*/download`、`/media/upload` 不套 #6 |
| 7 | Go → Node 单次渲染 | 30s | |
| 8 | Node 内部单页渲染软超时 | 25s | 必须 < #7，让 Node 先返回带上下文的错误 |
| 9 | Node Markdown 单文档软超时 | 15s | |
| 10 | Shiki 单代码块 | 预防式：>256KB 的代码块直接跳过高亮 | 正则回溯爆炸的主要来源 |
| 11 | 渲染器 `/health` | 3s | 连续 3 次失败 → 重启 |
| 12 | AI 单次 HTTP 请求 | 120s（`ai.timeout`） | 覆盖连接+读取全过程 |
| 13 | AI 整篇任务墙钟上限 | `min(batches × 120s × 1.5, 30min)` | 必须 > #12 |
| 14 | Job 心跳间隔 | 30s | |
| 15 | Job 僵死回收阈值 | 120s 无心跳 | 必须 > #14 × 3 |
| 16 | SSRF 出站抓取 | 10s | |
| 17 | 优雅关闭：HTTP | 15s | |
| 18 | 优雅关闭：等待 job | 15s | |
| 19 | 优雅关闭：Node SIGTERM → SIGKILL | 5s | |
| 20 | SSE 心跳 | 25s | 必须 < #3，否则 Nginx 会切连接 |

**实现要求**：把这张表写成 `internal/config/timeouts.go` 里的常量组，并加一个启动时的自检函数 `validateTimeoutOrdering()`，违反嵌套关系直接启动失败。这样将来改配置不会静默破坏。

## 3. 看门狗（Watchdog）

独立 goroutine，每 30s 执行一轮。这是"卡死"的唯一检测机制。

```go
func (w *Watchdog) Tick(ctx context.Context) {
    w.reclaimStaleJobs(ctx)      // §3.1
    w.timeoutTranslations(ctx)   // §3.2
    w.reclaimStaleRenders(ctx)   // §3.3
    w.checkRenderer(ctx)         // §3.4
    w.checkQueueDepth(ctx)       // §3.5
    w.checkDiskSpace(ctx)        // §3.6
    w.checkCircuitBreakers(ctx)  // §4
    w.detectStalls(ctx)          // §3.7
}
```

### 3.1 僵死 Job 回收（含心跳）

**这是前面文档的一个缺陷修正**：原来只按 `locked_at` 加固定 5 分钟阈值，但正常翻译任务可能跑 3~10 分钟，会被误回收。正确做法是**心跳**：

```go
// worker 在执行期间每 30s 更新一次
UPDATE jobs SET locked_at = ? WHERE id = ? AND locked_by = ?
```

看门狗：
```sql
UPDATE jobs SET status='pending', locked_by=NULL, locked_at=NULL
WHERE status='running' AND locked_at < datetime('now','-120 seconds')
```

**关键细节**：回收时 **不增加 `attempts`**。进程被 kill 不是任务本身的错，不应该消耗重试配额。只有任务自己返回错误才 `attempts+1`。

### 3.2 翻译任务墙钟超时

```sql
-- 超过 §2 #13 的上限
UPDATE translation_tasks SET status='failed', error='任务超时'
WHERE status='translating' AND started_at < datetime('now', ?)
```

同时取消对应的 job context。

### 3.3 渲染单元回收

`render_units.status='rendering'` 且 `updated_at < now-5min` → 重置为 `pending`。

### 3.4 渲染器健康检查与重启

```
每 30s GET /health（3s 超时）
  连续 3 次失败 → 判定 hung
    → SIGTERM，等 5s
    → 仍未退出 → SIGKILL   ★ 事件循环被阻塞时 SIGTERM 无效，必须 SIGKILL
    → 重启（指数退避 1s,2s,4s…最大 60s）
    → 重启后把所有 status='rendering' 的单元重置为 pending
```

**退出码 137（OOM Killed）的特殊处理**：不按普通崩溃处理，而是：
- 记录 `system_log`：`level=error, message="渲染器内存不足被终止"`
- **自动把 `render.concurrency` 临时降为 1**（本次运行期内），并在后台显示提示
- 若导致 OOM 的单元可识别（崩溃前最后处理的 unit），把它标记为 `failed` 并加入跳过列表，避免反复触发 OOM

### 3.5 队列积压告警

| 条件 | 动作 |
|---|---|
| `pending` job > 1000 | 后台顶栏黄色提示"任务积压 N 项" |
| `pending` job > 10000 | 红色告警 + 建议全量重建替代逐个渲染 |
| 队列深度 30 分钟内未下降 | 告警"任务处理似乎已停止" + 提供"重启渲染器"按钮 |

### 3.6 磁盘空间护栏

```
启动时 + 每 30s 检查 generated/ 所在分区可用空间：
  < 500MB → 后台黄色告警
  < 200MB → 拒绝新的全量重建（返回 507），增量渲染继续
  < 50MB  → 暂停所有写操作，进入只读模式，后台红色横幅
```

**发布前预检**：全量重建前估算所需空间（当前 release 大小 × 1.2），不足则拒绝并给出明确数字："需要约 180MB，当前可用 90MB"。

### 3.7 停滞检测（Stalled）

比"失败"更隐蔽的问题是**没报错但也不动**。

```go
// 每个运行中的任务记录 lastProgressAt
// 超过 stallThreshold 无进展 → progress.stalled = true
var stallThreshold = map[string]time.Duration{
    "render":    60 * time.Second,
    "translate": 180 * time.Second,   // AI 单批可能慢
    "backup":    120 * time.Second,
    "import":    60 * time.Second,
}
```

UI 表现：进度条变黄 + 文案"处理时间超出预期，仍在等待…" + 出现「取消」按钮。**不自动杀掉**——可能只是慢。给用户决定权。

## 4. 熔断器（Circuit Breaker）

AI provider 和渲染器都需要熔断，避免"坏了还一直打"烧钱和刷日志。

```go
type Breaker struct {
    failures    int
    state       State  // closed | open | half-open
    openedAt    time.Time
}
```

| 参数 | AI Provider | 渲染器 |
|---|---|---|
| 触发阈值 | 连续 5 次失败 | 连续 5 次失败 |
| 打开时长 | 60s（每次连续打开翻倍，上限 15min） | 30s |
| 半开试探 | 放 1 个请求过去 | 放 1 个请求过去 |
| 打开期间的行为 | 任务留在 `pending`，不消耗 `attempts` | 同左 |
| 用户可见 | 后台橙色横幅"AI 服务暂时不可用，将在 45 秒后重试" + 倒计时 | "页面生成服务暂时不可用" |
| 手动重置 | 后台「立即重试」按钮 | 「重启渲染器」按钮 |

**熔断打开时 `attempts` 不增加**——同 §3.1 的理由，外部服务不可用不是任务的错。

### 4.1 单元级熔断（毒丸隔离）

某个特定文章反复导致渲染崩溃（超大文件、畸形内容）会堵死整个队列。

```
同一 unit_key 24 小时内失败 > 10 次
  → 加入 poison list（内存 + system_log）
  → 停止重试，标记为 permanently_failed
  → 后台「渲染」页红色列出，附「查看错误」「强制重试」「查看源文件」
  → 全量重建时跳过，但计入 failed 统计
```

这保证**一篇坏文章不会拖垮整站**。

## 5. 降级矩阵

每个组件挂掉后，系统还能做什么、不能做什么。**这张表是产品承诺**。

| 故障组件 | 前台已发布内容 | 后台登录 | 编辑保存 | 发布 | 预览 | 翻译 | 媒体上传 |
|---|---|---|---|---|---|---|---|
| **Go 进程崩溃** | ✅ 完全正常（Nginx 直读） | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |
| **Node 渲染器崩溃** | ✅ 正常 | ✅ | ✅ | ⚠️ 内容已保存，页面排队等生成 | ❌ 降级为客户端简易预览 | ⚠️ 译文可生成，HTML 排队 | ✅ |
| **AI provider 不可用** | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ 任务排队 | ✅ |
| **SQLite 损坏** | ✅ | ✅ | ✅ | ⚠️ 队列丢失，触发全量重建 | ✅ | ⚠️ 进行中任务丢失，可重新触发 | ✅ |
| **磁盘满** | ✅ | ✅ | ❌ 明确报错 | ❌ | ✅ | ❌ | ❌ |
| **`generated/` 被删** | ❌ 直到重建完成 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| **`content/` 某文件损坏** | ✅ 其余正常 | ✅ | ✅ 其余正常 | ✅ | ✅ | ✅ | ✅ |
| **fsnotify 句柄耗尽** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |（降级为 5s 轮询）|

**⚠️ 的共同要求**：后台必须有**全局横幅**明确告知当前处于降级状态、影响是什么、预计如何恢复、用户能做什么。不允许静默降级。

### 5.1 全局状态横幅规格

后台顶部固定区域，同时最多显示 3 条，按严重度排序：

```
🔴 磁盘空间不足（可用 42MB）· 已暂停写入操作          [查看详情]
🟠 AI 服务不可用 · 3 个翻译任务排队中 · 45 秒后重试   [立即重试] [查看设置]
🟡 页面生成服务重启中 · 12 个页面等待生成             [查看渲染队列]
🔵 有 8 篇译文因源文更新而过期                        [批量更新] [忽略]
```

数据来自 `GET /api/admin/system/health` 的 `warnings[]`，SSE 推送变更。

## 6. 发布操作的完整 UX 时序

用户点「发布」后**每一秒**看到什么。这是本产品最高频的操作，必须打磨。

```
T+0ms     按钮进入 loading 态并禁用（防重复点击）
          乐观更新：状态徽章立即变为「发布中」

T+~150ms  API 返回 202 { queued: 12, jobId }
          按钮恢复，Toast: 「已发布 · 正在生成 12 个页面」
          顶栏出现进度指示器（小圆环 + 数字）
          编辑器状态区显示步骤条

T+0.5~3s  SSE 持续推送：done 从 0 → 12
          文章本身（priority 10）最先完成
          → Toast 更新为「文章已上线」，出现 [查看] 按钮（新标签打开前台）

T+3~6s    列表页、分类页、RSS、sitemap、搜索索引陆续完成
          进度指示器归零并消失
          最终 Toast: 「已全部更新 · 12 个页面」（3 秒后自动消失）
```

### 6.1 异常分支

| 情况 | 表现 |
|---|---|
| **渲染器不可用** | 202 仍然返回，Toast:「内容已保存。页面生成服务当前不可用，将在恢复后自动上线」+ 顶栏黄色横幅。**不阻塞用户**，可以继续写下一篇 |
| **超过 15s 未完成** | 进度指示器旁出现「生成较慢」提示，附「在渲染页查看」链接。**不弹窗、不阻塞** |
| **部分单元失败** | Toast:「文章已上线，但 2 个页面生成失败」+ [查看] 跳转渲染页 |
| **文章本身渲染失败** | 红色 Toast:「页面生成失败」+ 错误摘要 + [重试] [查看日志]。文章状态仍是 published（内容确实已保存），但列表中该行显示 ⚠️ 图标 |
| **用户在渲染完成前离开页面** | 无影响，后台继续。回来后可在渲染页看到结果 |
| **用户在渲染完成前再次编辑并发布** | 队列 dedupe，只渲染最新版本 |

### 6.2 「查看」按钮的正确时机

`[查看]` 按钮**只在该文章的 HTML 确实写盘后**才出现（依据 SSE 中 `unit.key == post:<locale>:<id>` 的完成事件）。过早出现会让用户点开看到 404 或旧版本——这是很多 CMS 的经典体验问题。

## 7. 翻译操作的完整 UX 时序

```
点击「翻译成 English」
T+0        按钮 loading，语言标签变为 ⏳
T+~100ms   202 { taskId }
           状态条:「正在分析文章结构…」（phase: segmenting，不确定态）
T+~300ms   分段完成，total 已知
           状态条:「翻译中 1/7 批 · 约 40 秒」+ 真实进度条
T+每批     进度推进，ETA 平滑更新
T+完成     状态条:「校验中…」→「生成页面…」→ 消失
           语言标签变为 ✓ completed
           Toast:「English 译文已完成 · 1,842 tokens」+ [查看] [编辑译文]
```

### 7.1 翻译的异常分支

| 情况 | 表现 |
|---|---|
| **某批失败重试中** | 进度条变黄，文案「第 3 批重试中 (2/3)」。**不隐藏这个信息**——用户有权知道 |
| **拆批降级** | 「第 3 批已拆分重试」 |
| **部分段落保留原文** | 完成后 Toast 为黄色:「译文已生成，但 4 个段落翻译失败并保留了原文」+ [查看详情] 列出具体段落位置 |
| **结构指纹校验失败（严重）** | 红色:「译文结构与原文不一致，已放弃」+ 具体原因（"代码块内容被修改"）+ [重试] [查看差异]。**不写入文件** |
| **AI 熔断中** | 任务显示「等待 AI 服务恢复 · 45s」+ 倒计时 |
| **stalled** | 「翻译响应缓慢，仍在等待…」+ [取消] 按钮出现 |
| **用户点取消** | 立即 context cancel，状态回到取消前（不写文件），已消耗 token 记入统计并告知用户 |
| **重复点击翻译** | 按钮在任务存在期间保持禁用；dedupe 保证服务端也不会重复 |

### 7.2 批量翻译的进度

翻译矩阵页批量触发 20 篇 × 3 语言 = 60 个任务时：

- 顶部总进度:「12/60 完成 · 3 失败 · 预计 8 分钟」
- 矩阵中每个格子独立显示自己的状态徽章，实时更新
- 提供「暂停队列」按钮（把 pending 任务标记为 paused，不影响 running）
- 失败的格子红色，hover 显示原因，点击可单独重试
- 全部完成后汇总卡片:「56 成功 · 3 失败 · 1 跳过（人工维护）· 共 128,400 tokens」

## 8. 编辑器的可靠性

这是用户投入最多心血的地方，**丢内容是不可接受的**。三层防护：

### 8.1 三层保存

```
第 1 层：本地即时（IndexedDB）
  每次输入变更后 500ms 防抖写入本地
  key = `draft:${articleId}:${locale}`
  存 { body, front, savedAt, baseHash }
  ★ 断网、崩溃、误关标签页都不丢

第 2 层：服务端草稿（HTTP）
  停止输入 2s 后 PUT /posts/{id}/draft
  失败时不打断用户，只在状态栏显示「未同步」+ 重试计数
  网络恢复后自动重试（指数退避，最多 5 次）

第 3 层：正式文件（用户显式操作）
  ⌘S 或点保存 → PUT /posts/{id}/content
```

### 8.2 恢复流程

进入编辑器时，按以下顺序比较三个来源的 `savedAt`：

```
本地 IndexedDB 草稿 / 服务端草稿 / 正式文件

若本地或服务端草稿比正式文件新：
  顶部显示恢复条（不自动覆盖，让用户决定）:

  ┌────────────────────────────────────────────────────────┐
  │ 📝 发现未保存的内容（本地 · 3 分钟前）                    │
  │    [查看差异]  [恢复]  [丢弃]                            │
  └────────────────────────────────────────────────────────┘
```

若本地与服务端草稿**都存在且不同**，显示两个选项并标注来源与时间。

### 8.3 网络与状态指示

编辑器状态栏永久显示同步状态，四种：

| 状态 | 显示 | 触发 |
|---|---|---|
| 已同步 | `已保存于 14:32` 灰色 | 服务端草稿保存成功 |
| 保存中 | `保存中…` + 转圈 | 请求进行中 |
| 未同步 | `未同步（本地已保存）` 黄色 | 服务端保存失败，本地成功 |
| 离线 | `离线 · 内容已保存在本地` 橙色 | `navigator.onLine === false` 或连续 3 次失败 |

**关键**：即使离线，用户也**照常能写**，不弹任何阻塞对话框。恢复网络后自动同步并变绿。

### 8.4 离开保护

```ts
// 存在未同步到服务端的变更时
window.addEventListener('beforeunload', (e) => {
  if (hasUnsyncedChanges) { e.preventDefault(); e.returnValue = ''; }
});
// SPA 内部路由跳转用 TanStack Router 的 blocker，弹自定义对话框（更友好）
```

### 8.5 冲突处理 UI

409 返回时弹出三栏对比对话框：

```
┌──────────────────────────────────────────────────────────────┐
│ 内容冲突                                                       │
│ 这篇文章在你编辑期间被修改过（14:35，来自 admin）                │
│                                                              │
│  你的版本          │  服务器版本        │  差异                 │
│  ─────────────────┼──────────────────┼─────────────────────  │
│  （只读预览）       │  （只读预览）      │  （行级 diff）         │
│                                                              │
│  [保留我的（覆盖）]  [使用服务器的（放弃我的）]  [下载我的副本]     │
└──────────────────────────────────────────────────────────────┘
```

「下载我的副本」把当前内容存成 `.md` 文件下载——**永远给用户一条保住自己劳动成果的退路**。

### 8.6 大文档性能

| 文档规模 | 要求 |
|---|---|
| 5 万字 | 输入无感延迟 |
| 20 万字 | 输入延迟 < 50ms；预览防抖提高到 800ms |
| > 50 万字 | 自动关闭实时预览并提示；语法高亮降级为仅当前视口 |

CodeMirror 6 默认虚拟化，主要风险在**预览请求**——必须防抖 + `AbortController` 取消旧请求。

### 8.7 上传中断

| 情况 | 处理 |
|---|---|
| 上传中断网 | 队列项标红 + [重试]，编辑器中的占位符 `![上传中...]()` 变为 `![上传失败,点击重试]()` |
| 上传中关页面 | 已完成的保留，未完成的丢弃；重进后编辑器里的失败占位符仍在，可删除或重试 |
| 文件过大 | **前端先校验**，不发起请求，直接提示"文件 32MB，超过上限 20MB" |
| 同名文件 | 自动加序号，不询问（询问会打断写作流） |

## 9. SSE 断线与降级

SSE 是所有实时体验的基础，它断了必须让用户知道。

```ts
const es = new EventSource('/api/admin/events');

es.onerror = () => {
  setConnState('reconnecting');
  // EventSource 自动重连，但要有上限
  if (++retries > 5) {
    setConnState('polling');
    startPolling();      // 降级为每 5s 轮询 /system/health + /render/status
  }
};

es.onopen = () => {
  retries = 0;
  setConnState('live');
  queryClient.invalidateQueries();   // ★ 重连后必须刷新，补上断线期间错过的变更
};
```

| 状态 | UI |
|---|---|
| `live` | 无提示（正常态不打扰） |
| `reconnecting` | 顶栏细灰条「正在重新连接…」 |
| `polling` | 顶栏黄条「实时更新不可用，已切换为定时刷新」+ [重试] |

**心跳**：服务端每 25s 发 `: ping`（必须 < Nginx 的 `proxy_read_timeout`）。客户端 40s 未收到任何数据主动重连（EventSource 自身不检测半开连接）。

## 10. 幂等性与重复提交

| 场景 | 防护 |
|---|---|
| 重复点发布 | 前端按钮禁用 + 服务端 dedupe key（同一 article+revision 的发布是幂等的） |
| 表单重复提交 | 提交中禁用；成功后跳转或重置 |
| 浏览器重试 POST | 写操作端点接受可选 `Idempotency-Key` 头，服务端缓存 5 分钟内的响应（内存 LRU，1000 条） |
| 重复触发全量重建 | 已有 running 的 rebuild 时返回 409 + 现有 jobId，前端跳转到该进度 |
| 重复上传同一文件 | 按 sha256 检测，提示"该文件已存在"并给出现有 URL，可选择仍然上传副本 |
| 重复创建同 slug | 服务端 422，前端在 slug 输入框实时校验（防抖 500ms 查重） |

## 12. 错误文案规范

### 12.1 三层错误信息

每个错误有三层，给不同的人看：

```json
{
  "error": {
    "code": "RENDER_FAILED",
    "message": "页面生成失败",                    // ← 给用户：说人话，不含技术术语
    "detail": "文章「我的服务器搭建记录」的英文版本生成失败：代码块语言 'foobar' 无法识别",
                                                 // ← 给用户：具体是什么、在哪
    "hint": "请检查文章中的代码块语言标识，或在设置中添加该语言",
                                                 // ← 给用户：能做什么
    "trace": "shiki: unknown language...",       // ← 给开发者，仅 dev 模式返回，生产写日志
    "requestId": "01J..."
  }
}
```

### 12.2 文案规则

| 规则 | 反例 | 正例 |
|---|---|---|
| 不暴露内部实现 | `EOF while parsing yaml at line 3` | `文章元数据格式错误（第 3 行）` |
| 不说"未知错误" | `发生未知错误` | `保存失败，请重试。若持续失败请查看系统日志（错误码 01J…）` |
| 说明影响范围 | `翻译失败` | `英文译文生成失败，其他语言不受影响` |
| 给下一步动作 | `AI 服务不可用` | `AI 服务不可用，任务已排队，将在服务恢复后自动继续` |
| 不指责用户 | `你输入的 slug 非法` | `固定链接只能包含字母、数字和连字符` |
| 数字要具体 | `文件太大` | `文件 32MB，超过上限 20MB` |

### 12.3 requestId

所有错误响应带 `requestId`，与服务端日志的 `request_id` 字段对应。用户报错时提供这个 ID 即可精确定位。UI 上小字显示 + 点击复制。
